# 角色
你是一位资深全栈工程师与技术文档专家。请阅读当前代码库，生成一份结构化、模块化、token 高效的项目知识库。

# 目标
使我后续「修改功能」或「查询数据」时，无需再阅读源码即可：定位关键文件、理解数据流向、知晓注意事项。

# 设计原则
1. 分层模块化：一份「索引总览」+ 多份按模块/主题拆分的独立文档，便于后续按需加载某一篇而非全量加载。
2. 事实导向：只记录代码中真实存在的内容，不臆测、不补充未实现的设计；拿不准时标注「待确认」。
3. 精炼可操作：用列表和表格，避免冗长叙述；每条信息都要能直接指导操作。
4. 路径必标：所有关键文件、配置、数据位置都必须标注仓库内相对路径。
5. 版本必标：记录关键依赖的大版本号。

# 输出结构（全部存放在 docs/knowledge-base/ 下）

## 1. INDEX.md —— 索引总览（后续每次对话优先加载这一份）
- 项目一句话定位
- 核心功能清单：功能 → 所属模块 → 入口文件路径
- 技术栈表：类别 | 技术/库 | 版本 | 用途
- 仓库拓扑：目录树，每个目录标注职责（monorepo 需标注 workspace 划分）
- 模块依赖关系：文字版依赖图
- 数据流向总览：输入 → 处理 → 存储 → 输出（一行链路 + 关键节点文件）
- 速查表：常见任务（如「新增一个 API」「改某端页面」「查某类数据」）→ 涉及文件路径
- 文档导航：列出本知识库所有文档及其适用场景

## 2. ARCHITECTURE.md —— 架构与数据流
- 整体架构说明（各端/各服务职责划分）
- 跨端/跨服务通信方式
- 数据模型定义：Schema、字段、关系（用表格）
- 数据存储位置与格式
- 数据同步/流转机制（如 Git 同步、定时任务、消息队列等，标注触发源与配置文件路径）

## 3. modules/<模块名>.md —— 每个核心模块一份
- 模块职责
- 入口文件路径
- 关键文件清单：文件路径 → 职责
- 对外暴露的接口/导出
- 依赖了哪些模块 / 被哪些模块依赖
- 修改本模块时的注意事项与红线

## 4. API.md —— 接口清单
表格列出所有对外接口：路径 | 方法 | 入参 | 出参 | 鉴权方式 | 处理函数文件路径

## 5. DATA.md —— 数据查询指南（重点，对应你「查数据」诉求）
- 数据实体清单：实体 → 存储位置 → 文件路径
- 常见数据查询场景：我想查 X → 去哪个文件/表/集合 → 用什么方式查
- 数据变更链路：谁写入 → 存在哪 → 谁读取

## 6. OPERATIONS.md —— 构建与运维
- 环境变量清单：变量名 | 用途 | 是否必填 | 默认值
- 本地开发启动步骤（分端/分服务）
- 构建/部署命令
- 定时任务/Cron 配置：任务 → 触发时机 → 处理文件路径
- CI/CD 流程概要

## 7. CONVENTIONS.md —— 约定与陷阱
- 代码风格与命名约定
- 文件组织约定
- 已知问题 / 历史包袱 / 易踩的坑
- 修改红线：哪些东西不能动、动了会破坏什么

# 执行步骤
1. 先读根目录配置文件（package.json / pnpm-workspace.yaml / 各类 config / lock 文件），确认技术栈与 workspace 划分。
2. 浏览各 workspace 入口文件，建立模块地图，先产出 INDEX.md 草稿。
3. 按上述结构逐一生成其余文档，每写一节前先核对对应源码，确保路径与字段真实存在。
4. 全部完成后，在 INDEX.md 顶部写「使用说明」：何时加载哪份文档、如何更新知识库。

# 维护约定
- 知识库与代码同仓库，放在 docs/knowledge-base/。
- 每份文档顶部标注：最后更新日期 + 对应 commit hash（短）。
- 涉及架构/接口/数据模型变更时，同步更新对应文档；纯实现细节变更不必更新。
